# Thermostat templates

`cbus-toolkit thermostat template` reproduces the Toolkit thermostat **Load Template** dialog on one closed database unit: the native PP overlay, then the dialog's later object-model adjustments and form save for the fields they touch. `--overlay-only` (Python `post_load=False`) keeps the pure native overlay.

```sh
export CBUS_UNITSPEC_DIR=/private/decoded/unitspec

cbus-toolkit thermostat template list --unit-type PC_TSB

cbus-toolkit thermostat template preview //HOME/254/p/4 --template 2 \
  --host 127.0.0.1 --port 20023 --exclusive-project

cbus-toolkit thermostat template apply //HOME/254/p/4 --template 2 \
  --host 127.0.0.1 --port 20023 --exclusive-project --backup-project HOMEBAK
```

Template specifications are read from `--spec-dir`, or from `CBUS_UNITSPEC_DIR` when that option is omitted. They are never bundled. The connected C-Gate must also hold the same files in its own unit specification directory, because the apply step asks it to load one of them.

## Compatibility

The original installation list depends only on the thermostat class:

| Unit types | Class | Offered templates |
| --- | --- | --- |
| PC_TSA, PC_TSA5 | TProgrammableThermostat | `THERMOSTATA_TEMPLATE01`–`09` |
| PC_TSB, PC_TSB5 | TBasicThermostat | `THERMOSTAT_TEMPLATE01`, `04`, `05`, `06`, `08`, `09` |

The CLI refuses other unit types and the templates the original never offers. This includes basic templates 2, 3 and 7, even though C-Gate contains those files. Native `PP LOAD_FROM_FILE` itself accepts any file with any unit type, so the refusal happens before any I/O. Every template declares firmware `0`–`9`. The CLI checks that range, while the original performs no firmware check. Each `THERMOSTATA` template includes the `THERMOSTAT` template with the same number, then overrides and extends it.

The catalogue loader also requires each template parameter to meet these checks:

- It is one byte with a default value.
- Its name and address match the unit specification (`THERMOSTATA.xml` or `THERMOSTATB.xml`).
- It is within that specification's range.
- It does not alias any other parameter byte.

## Overlay semantics

The Toolkit sends `PP LOAD_FROM_FILE <session> <template>` with no `PP RESET_TO_DEFAULTS` first. C-Gate writes only the template's declared bytes, which are 59 parameters for basic templates and 61 for programmable ones. Every other parameter keeps its current value. Preview computes this overlay independently from the specification and reports the following:

- The parameters that change, with before and after values.
- The template parameters that already match.
- The number of parameters that are preserved.

## Post-load replay

After the load the original dialog changes its in-memory model, and the form writes the model back on its next save. The replay reproduces the result of that save for the fields the pipeline touches. The recovered steps are:

1. The parent `HandleBeforeLoadTemplate` event sets the thermostat's template-load flag (`+0x1e0`). `ClearOriginalDamperGroups` clears four retained damper references. These have no PP effect.
2. A master/slave value of 1 is set to 0 before loading. AfterLoad then derives master/slave from `ControlledZones` (master when it is above 0), so the pre-load value never persists.
3. AfterLoad resolves each output group. The internal plant type is virtualised first: unit type 8 becomes virtual type 11 (fan coil) unless all cool outputs and the three heat fan outputs are 255. For each output address the loader keeps an existing group without the thermostat prefix. Otherwise it creates or renames a group tagged `[CGnn] <default name>`, where `nn` is the `ZoneGroup` address and the default name depends on the plant type and installation. If the plant type has no such output, it keeps an existing group or uses the unused group 255 (`<Unused>`, created if missing). Programmable units treat dampers the same way with `Damper Zone N`. Basic units always save dampers as 255.
4. While the template-load flag is set, AfterLoad skips all five relay-group reads. Stale relay addresses therefore neither create groups nor block the replay. `UpdateParametersForPlantType` reassigns every cool/heat output and all five relays in every plant branch, by virtual plant type and, for types 3 and 9, by installation name. A named output first reuses a group with the autogenerated tag, then creates one at its default address. It can also take over a prefixed group at that address when no other output uses it.
5. `UpdateFanSpeedsForPlantType` sets eight heating/cooling fan settings by plant type.
6. On programmable units `UpdateEvapProgramParameters` clears `EvapProgramEnabled`. It also clears `NonEvapProgramEnabled` for virtual plant types 0 and 2. The parent `HandleLoadTemplate` event then clears the template-load flag.
7. The form save (`BeforeSaveProgrammingInformation`) writes the model back with these rules:
   - Groups are written by address.
   - Virtual type 11 is saved as 8. A slave saves `InternalPlantType` and `InternalPlantZones` as 0 and every damper as 255.
   - Fan settings follow the interlock described in [thermostat-settings.md](thermostat-settings.md).
   - `DamperModulationEnable` is written as 0, 2× or 3× its flag for plant types 0, 2 and 6/10, and 1× otherwise.
   - `EnableHVACRelayDrive` is written as 0.
   - `InstallationCode` is the installation number.

`preview` reports `post_load` with the replayed parameters, the parameters that differ from the plain overlay and the planned group operations. In a fresh output application, templates 1 and 2 gain a `B (cool activation)` output on group 2, and templates 5 and 6 get the evaporative/fan-coil heating fan settings and lose unused heat activation.

The output application is named by the thermostat's scalar `ApplicationNumber` parameter. It must exist in the network. Original AfterLoad resolves that application and writes `TCBUSUnit.ApplicationObject`; the plant getters use that same object. The generic `Application` array does not select thermostat output groups. Earlier acceptance receipts predate this corrected lookup; the new focused receipt includes a deliberately different generic application and verifies it is preserved.

The replay fails closed when:

- The unit has no valid `ApplicationNumber` byte or its application is absent.
- The output application already contains a group tagged with this thermostat's `[CGnn]` prefix. The original's template-flag-dependent rename/reuse sequence is recovered but not yet reproduced for this case.
- Several groups share an autogenerated tag.
- A step would reach the original `GetNewGroup` search without the explicit bounded profile below.

In a fresh application, installation 9 reaches `GetNewGroup`: `W2 (heat)` requests default group 5, already used by `Y (cool)`. Depending on the group-manager collection order, the recovered search can select group 4 or 7. The replay does not infer that collection order from database XML.

Use `--group-sort address-ascending` (Python `group_sort='address-ascending'`) to declare the original process's address sort context. This profile requires an initially empty output application and post-load replay. It excludes applications 172 and 203, whose separate zone/remote group effects are outside this replay. It neither reads nor assumes a saved Toolkit preference. A preexisting group, even `<Unused>`, is refused under this profile.

For example, append `--group-sort address-ascending` to template 9 preview/apply in a fresh output application. Original insertion and allocation then produce relays `[5,2,3,6,7]`: Y, Y2, G, W and W2. The [original-instruction receipt](../research/experiments/2026-09-30/thermostat-group-order-runtime.json) checks 36 comparator cases, all 120 insertion permutations of the five starting addresses and 9 search cases. It executes the original comparator, insertion-position and allocation-search instructions against declared synthetic objects; Python maintains the inventory and the search stops before original object creation. The [load-boundary receipt](../research/experiments/2026-09-30/thermostat-group-load-boundary-static.json) pins the application-selection path and shows why cached references do not establish general sortedness.

Existing managers can receive unsorted references before `LoadAndSort` or a deferred sort completes. Their initialization and sort state are not established by the database snapshot. Locale-sensitive tag ordering, preloaded ordering and other sort modes remain unsupported.

The replay does not reproduce the generic AfterLoad/BeforeSave normalisation of fields the pipeline does not touch. It also leaves out AfterLoad's creation of applications 115/116 and the air-conditioning zone group. Its tables are pinned by a [static receipt](../research/experiments/2026-09-30/thermostat-post-load-static.json):

```sh
python research/thermostat_post_load_static.py --exe CBusToolkit.exe --map CBusToolkit.map
```

The [group-phase receipt](../research/experiments/2026-09-30/thermostat-group-allocation-static.json) separately pins the parent/child event wiring, the relay-load skip and the independent five-relay assignment proof for every plant branch. It also records the remaining allocator boundary: `GetNewGroup` walks same-prefix groups in reverse manager order, searches for a free address above each through 254, then falls back to the lowest free address from 0 through 254. `FindExistingGroup` instead takes the first case-insensitive tag match in forward manager order. The ordinary-load relay default tags are recovered too, but that phase is skipped during Load Template. Reproduce this receipt with `research/thermostat_group_allocation_static.py` and the same `--exe` and `--map` arguments. These are static checks; the original dialog was not executed.

## Apply

The unit path is `//PROJECT/network/p/unit`. Every network in the project must be closed with synchronization idle. `--exclusive-project` declares that the caller controls all editing and reloading of the project; the command does not acquire a server-wide lock. Planning makes these reads:

- The unit XML.
- One read-only PP snapshot. The command rejects it if the read changed the database XML.

Apply takes these steps:

1. Recheck the unit XML, PP snapshot and network inventory.
2. If neither parameters nor groups would change, return `already_applied` without writing anything. A plan with only group creations still applies and verifies them.
3. Otherwise, save the project and copy it to a backup. The backup name is either `--backup-project` or a random new name.
4. Recheck the unit.
5. Open a PP session and issue the original `LOAD_FROM_FILE`.
6. Compare every staged parameter with the plan. Any template mismatch or unrelated change stops the operation before saving.
7. With the replay, set the post-load parameters, compare again, then create or rename the planned output-application groups (`DBADDSAFE`/`DBSETSAFE`).
8. Issue one `PP SAVE_TO_SOURCE` and one target `PROJECT SAVE`.
9. Close and reload the project.
10. Verify the result in a fresh session. The template and replayed values must match the plan, every other parameter must be unchanged, the unit identity (OID, type, firmware, catalogue number) and its non-PP XML must be unchanged, and the output application must hold exactly the planned groups.

The command makes no retry and no automatic rollback. `pp_save_attempted`, `pp_save_confirmed`, `target_save_attempted`, `target_save_confirmed` and `outcome_uncertain` identify an interrupted save. Inspect those fields and the backup before any recovery. Each plan allows one apply attempt.

The Python API is `NativeThermostatTemplates(client, ThermostatTemplateCatalog(spec_dir)).plan(path, number, exclusive_project=True)`, followed by `apply(plan, backup_project=...)`. The offline helpers are `plan_overlay` (pass `groups=` to replay the post-load pipeline), `compare_overlay` and `thermostat_post_load.replay_post_load`.

## Evidence and limits

- **Static review.** [thermostat-template-static.json](../research/experiments/2026-09-29/thermostat-template-static.json) pins the installation table, the class chains, the no-reset `LoadFromTemplate` sequence, the post-load call order and the help topics searched against the original EXE and MAP.
- **Offline tests.** Six tests with four subtests use synthetic specifications (`tests/test_thermostat_templates.py`).
- **Native acceptance.** Owned C-Gate 3.4.0.2001 passed three tests: [receipt](../research/experiments/2026-09-29/thermostat-template-native-acceptance.json).
  - All 15 offered pairs were applied: 9 programmable templates on PC_TSA/PC_TSA5 and 6 basic templates on PC_TSB/PC_TSB5.
  - Before each apply, every template parameter was set one step away from its template value, and three unrelated parameters were set to non-default values.
  - After save, close and reload, every template value equalled an expected value that the test computed independently from the raw template XML. Every other parameter was unchanged.
  - The test refused basic templates 2, 3 and 7 and a KEY4 unit, and the project stayed byte-identical.
  - A public CLI preview and apply also passed.
  - No CNI connection occurred. The service stayed on loopback, and its process and storage were removed.

- **Post-load replay.** Focused offline tests (`tests/test_thermostat_post_load.py`) check hand-derived expectations, including ignored stale relay addresses in both families. Owned C-Gate 3.4.0.2001 passed three tests: [relay-phase receipt](../research/experiments/2026-09-30/thermostat-post-load-relay-native.json).
  - 13 admitted pairs were applied (PC_TSA templates 1–8; PC_TSB templates 1, 4, 5, 6 and 8), each in its own fresh output application with a pre-set `EvapProgramEnabled`.
  - Every saved value equals the plan. For four pairs, the values and the group tags equal hand-derived expectations.
  - A prior snapshot with five stale relay addresses was saved/reloaded in each family. Template 1 produced literal relay values `[1,2,3,4,255]`, exact hand-derived tags and no groups for the stale addresses. The native overlay itself replaces those prior bytes; the static proof and offline post-overlay stale-relay cases establish the skipped original phase.
  - The focused native test checks installation 9's allocation refusal in both families, a unit without an `Application` byte and an existing `[CG01]` group, with the project unchanged after refusal. Consult the receipt for the cases actually run.

- **Explicit allocation profile and application selection.** The [focused acceptance receipt](../research/experiments/2026-09-30/thermostat-group-profile-focused-acceptance.json) records 31 offline tests plus 572 subtests and seven owned native tests, repeated against an installed wheel whose 258 package files match source. New cases cover all four aliases through public CLI template9 preview/apply, exact relay/group results, changed and nonempty inventory refusals, group-only saves, and preservation of a different generic `Application`. Native save/reload retained unrelated parameters and unit XML; the CNI sentinel saw no connections and both owned services were removed. No full suite or original whole-form run was performed.

The following remain open:

- Generic AfterLoad/BeforeSave normalisation of untouched fields, `GetNewGroup` outside the explicit empty/address-ascending profile, existing-prefix rename/reuse, ordinary-load group side effects and the full original dialog/form execution.
- Captions and images shown in the dialog.
- Per-byte protection that `LOAD_FROM_FILE` copies from the template.
- cmqttd `LOAD_FROM_FILE` overlay parity. Staged verification refuses to save a non-overlay result.
- Physical thermostats.
