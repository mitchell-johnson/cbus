# IOPE scene selectors

`IopeSceneSelectors` implements one bounded original scene-header component for IOPE1R1, IOPE2R2 and IOPE2C4 firmware 1.0.00..1.2.99. Select one existing normal action or all-off action in scene 1..4. The existing Trigger group stays fixed. This is component persistence through staged PP; it does not execute the whole original SceneManager accepted-dialog save or IOPE SaveScenes.

The API is `plan(current, identity=(type, firmware, catalogue), scene=2, normal_selector=30, group_cache=cache)`, or use `all_off_selector` instead. Exactly one selection is required. `show` is read-only and does not resolve object presence. `apply` verifies native profile/schema, replays the canonical plan, rejects stale guarded parameters, stages and verifies the one changed array and rolls it back on failure. It never saves. The caller owns any reviewed database PP SAVE and fresh reload.

The cache has exactly `format`, `source`, `applications` and `action_selectors`. Format is `cbus-iope-scene-selector-groups-v1`; source is a nonblank caller evidence description. Applications are `{address, groups}` rows containing existing primary Lighting and Trigger group addresses. Exactly one action inventory row is required: `{application:202, group:<retained Trigger group>, addresses:[...]}`. That list declares the complete existing LevelManager inventory for the target group. All values are exact integers, duplicate entries are refused, and lists are sorted canonically. Same-group Level identity is represented by `(202, group, address)`. The original loads by Address and saves AddressAsString; a Level Value is not the selector encoding and need not equal Address. Caller metadata alone is not a fresh database observation.

Admission deliberately requires a stable positive graph: primary Lighting app48..95; a non-255 Trigger group; all eight normal/all-off selectors distinct and positive1..254, resolved in the declared inventory; SceneIndex0..3; SceneTablePointer178,194,210,226; and four eight-command scenes whose group bytes are non-255, positively existing primary Lighting groups and distinct within each scene. The original LoadScenes collapses duplicate group commands before header initialization, so duplicates are refused. The selected action must exist and must differ from the opposite selector and both selectors in every other scene. Selecting the already-retained own action is a no-op.

Only ActionSelector($A6,4bytes) or ActionSelectorAllOff($AA,4bytes) may change. Whole-array PP staging preserves its other three entries. Application, SceneTriggerGroup, SceneIndex, SceneCommandRampRate, SceneTablePointer and all64 SceneTable bytes are guarded dependencies and are preserved. Other input/microfunction/join fields are outside write ownership. Bit masks preserve unused SceneIndex bit3. No group/action creation, Trigger group change, unassigned selectors, external0x9d pointers, pointer observation probes, input ramp edits or physical operations are admitted.

Source evidence is `research/fixtures/iope-scene-selectors-source-review.json`: exact EXE/MAP/UnitSpec/resource hashes, static method byte-span hashes and a synthetic byte vector. The exact IOPE scene bridge reaches ExecuteSceneManagerForInputUnit0xf87894, which selects type2 and an eight-command scene limit. SetupActionSelectorCombo0xf87e48 binds ActionSelector; SetupActionSelectorAllOffCombo0xf87f14 binds ActionSelectorAllOff to the selected temporary scene. Both exact source resource controllers use umChange. Their list inclusion filter0xf87aa8 excludes existing level objects used by another scene or the opposite selector. Trigger initialization0xf8c3c8 re-resolves the selected retained actions into the fixed group; admitted complete positive metadata makes this resolution stable and creates nothing. Header reference setters only assign the selected reference.

Whole SaveNeoScenes rebuilds commands across the collection. Whole IOPE SaveScenes repacks content/pointers and normalizes SceneIndex, and its external-pointer/session-dependent branch can load SceneTablePointer through PP to disable content writes. Those broader lifecycles remain excluded even for this canonical graph. Source-static component receipts and synthetic unit checks are not original GUI execution, whole-tab parity, or physical acceptance.
