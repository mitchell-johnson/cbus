`research.windows_bridge.WindowsBridge` now recognizes only the exact observed UTM status/message and requested path as `WindowsFileBusyError`, and only for a file pull. Direct `result()` calls still raise that typed error. `wait()` retries reads only of the same job's `.result.json`, `.stdout.txt` and `.stderr.txt` artifacts. It never resubmits a job or retries compilation, model execution, file writes, admission, unrelated paths or other errors.

`wait(job_id, timeout=330, max_busy_retries=8)` retains the existing polling interval of at most 0.5 seconds. The retry count is configurable from zero through 256. One retrieval deadline bounds every subprocess pull and poll; an individual pull also retains the existing 120-second maximum. Late retrieval is rejected. The deadline begins when `wait()` starts, after submission; this is not an end-to-end submission timeout or a strict operating-system scheduling guarantee. Invalid options are rejected before `run()` submits anything.

Successful results include detached `wait_evidence`, with ordered busy attempts, requested paths and original stderr. Failures preserve the original exception and expose the same evidence when attachment succeeds; `last_wait_error` and `last_wait_evidence` provide instance fallbacks. Each operation resets those fallbacks. Exhausted retries or timeouts do not authorize job replay.
